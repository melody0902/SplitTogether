一、專案目標與範圍

專案名稱：SplitTogether
使用情境：朋友旅遊、聚餐或共同活動，由成員代墊支出，再計算各自負擔與還款金額。

主要流程：
Google 登入 → 建立群組 → 邀請成員 → 新增支出 → 查看分帳 → 記錄還款。

第一版限制：
1. 只提供 Google 登入，不實作帳號密碼、忘記密碼或其他登入供應商。
2. 所有正式群組成員都必須登入，不提供未註冊的虛擬成員。
3. 每個群組只有一種幣別，第一版固定 TWD，金額最多兩位小數。
4. 每笔支出只有一位付款人。
5. 支援平均分攤與自訂金額。
6. 還款採人工記錄，不串接銀行或金流。
7. 不實作多幣別、收據 OCR、附件、通知、即時聊天、週期支出。
8. 不建置平台管理員後台。
9. 本次目標為本機可啟動、可驗收的 MVP，不要求實際部署雲端。

三、Google 登入

使用後端主導的 Google OAuth 登入流程：
1. 前端按鈕導向後端登入端點。
2. 後端透過官方 Google authentication handler 發起驗證。
3. 由 middleware 處理 Google callback，使用短效 external cookie。
4. 應用程式完成使用者查找或建立後，核發自己的登入 Cookie。
5. 清除暫存 external cookie，導回前端。
6. Google 取消授權、失敗與過期都要有可理解的畫面。

身份設計：
- Users 儲存應用程式使用者。
- ExternalLogins 儲存 UserId、Provider、ProviderUserId。
- Provider + ProviderUserId 必須唯一。
- 以 Google 提供的穩定使用者識別建立關聯，不使用 email 當主鍵。
- 不因 email 相同自動合併不同供應商帳號。
- 第一次登入建立使用者，後續登入更新必要的顯示名稱與頭像資料。
- 保留未來增加供應商的資料結構，但不提前實作其他登入功能。
- 不要求額外 Google API 權限，不保存不需要的 access/refresh token。

登入安全：
- 使用 HttpOnly Cookie，正式環境 Secure。
- 正確配置 SameSite、OAuth correlation cookie、state 驗證。
- 只允許本地白名單 returnUrl，防止開放重新導向。
- 不將登入權杖放進 localStorage。
- API 未登入回 401，權限不足回 403，不回 HTML 登入重新導向。
- 所有會修改資料的 API，包括登出與接受邀請，使用防 CSRF 機制。
- 提供取得 antiforgery token 的方式，串接 Angular XSRF header。
- 登入後重新取得 antiforgery token。
- Cookie 到期、401 時前端清除狀態並引導登入。
- 提供合理的工作階段有效期限，並寫入文件。

開發與正式環境以同源方式為主要設計：
- 開發環境使用 Angular proxy。
- 將 /api、Google callback 等必要路徑正確代理到後端。
- 文件明確列出瀏覽器 URL、API URL、callback URL 與 HTTPS 設定。
- 正式環境提供同源反向代理或 ASP.NET Core 託管前端的做法。
- 若需要 CORS，只允許明確設定的 origin，不搭配 credentials 使用萬用 origin。
- 容器執行時應考慮 Data Protection keys 的持久化。

憑證：
- Google ClientId、ClientSecret 使用環境變數或 dotnet user-secrets。
- 不提交密鑰，不在記錄中輸出 token、cookie 或 secret。
- 提供設定範例與 Google Cloud OAuth 設定步驟。
- 若缺少憑證，完成其餘功能及登入設定說明，明確列出尚未完成的人工驗證。
- 不要因缺少 Google 憑證停下整個開發。
- 測試可使用僅限測試環境的 authentication handler；不可在正式環境開啟假登入。

四、群組與邀請

群組資料：
- 名稱：必填，最多 100 字。
- 描述：選填，最多 500 字。
- 幣別：TWD，不可修改。
- 擁有者、建立時間。
- 群組建立者自動成為 Owner。

角色：
- Owner：管理群組、邀請、移除成員、管理所有支出及還款。
- Member：查看群組帳務、新增支出、管理自己建立的支出。
- 不提供所有權移轉，Owner 不可移除自己。

邀請：
- Owner 可以產生、撤銷邀請連結。
- 使用密碼學安全亂數 token，資料庫只保存 hash。
- 有效期限預設 7 天。
- 連結有效期間可供多位使用者加入，直到過期或撤銷。
- 開啟連結不直接加入，必須登入並按「確認加入」。
- 加入前只呈現必要的邀請資訊，不公開支出或成員帳務。
- 已加入成員重複接受時回傳既有結果，不產生重複成員。
- 過期、撤銷、無效 token 顯示清楚訊息。
- 不實作寄信，由使用者複製連結分享。
- 不在 logs 記錄邀請 token。
- 邀請查詢與接受端點加入合理 rate limiting。

移除成員：
- 只允許移除從未有帳務關聯的非 Owner 成員。
- 曾是支出建立者、付款人、分攤者、還款登記者、付款方或收款方者不可移除。
- 已刪除或作廢的帳務紀錄仍算歷史關聯。
- 被移除後不得再讀取群組資料。
- 不提供刪除群組，避免誤刪帳務。

五、支出管理

欄位：
- 標題：必填，最多 100 字。
- 總金額：大於 0，最多 1,000,000,000.00 TWD。
- 支出日期：date-only，依使用者選擇保存。
- 付款人：一位現有群組成員。
- 分攤方式：Equal / Custom。
- 分攤成員：至少一位現有群組成員。
- 備註：選填，最多 1,000 字。
- 建立者、建立與更新時間、版本號。

規則：
- 付款人不一定參與分攤。
- 任一成員可以替群組其他成員記錄代墊，但保留實際建立者。
- Member 只可修改、刪除自己建立的支出；Owner 可管理全部。
- 修改與刪除需要確認與版本檢查。
- 刪除採軟刪除，不影響歷史關聯檢查。
- 每次變動立即反映最新群組餘額。
- 即使已有還款仍允許更正支出；保留還款歷史並重新計算，必要時可能產生反向應付款。
- UI 應提醒使用者更正可能改變結算結果。
- 付款人、分攤成員必須屬於 URL 指定的同一群組。
- 分攤名單不可重複。
- 前後端都驗證，後端為最終權威。

支出列表：
- 分頁，預設每頁 20 筆，上限 100。
- 依日期新到舊排序，使用穩定的次排序鍵。
- 支援標題搜尋、日期區間、付款人篩選。
- 可進入詳情、編輯、刪除。
- 顯示建立者，避免與付款人混淆。

六、金額與分攤規則

避免浮點誤差：
- 資料庫金額使用 bigint，單位為分。
- 後端使用 long，運算使用溢位檢查。
- API 金額以最小單位整數傳遞，欄位以 Minor 結尾。
- API 拒絕超出 JavaScript safe integer 範圍的整數。
- 前端從十進位字串精確轉換成分，不直接以浮點乘除當作帳務邏輯。
- 群組彙總若超出 API 安全整數範圍，回傳明確錯誤，不可靜默截斷。

平均分攤：
- 以整數除法取得每人基礎金額。
- 餘數以穩定的 GroupMemberId 順序，每人加 1 分。
- 前端預覽與後端使用相同、文件化的排序方式。
- 100 元由三人分攤，結果為 33.34、33.33、33.33。
- 實際分攤結果存入 ExpenseSplits，不在每次查詢時重新分配。

自訂分攤：
- 每人金額可為 0，不可為負數。
- 分攤合計必須完全等於支出總額。
- UI 即時呈現尚未分配或超額的金額。

七、餘額與結算

每位成員顯示：
- 已代墊總額。
- 應負擔總額。
- 已付還款總額。
- 已收還款總額。
- 淨餘額。

計算：
淨餘額 = 已代墊 - 應負擔 + 已付還款 - 已收還款

正數：應收。
負數：應付。
零：已結清。

規則：
- 只計算未刪除支出及未作廢還款。
- 群組所有成員淨餘額總和必須為 0。
- 還款不計入群組消費總額。
- 餘額由帳務紀錄計算，不設計容易失去同步的可修改 balance 欄位。

結算建議：
- 將淨應付者與淨應收者配對。
- 使用確定性的 greedy 演算法：按金額絕對值排序，同額以 MemberId 決定順序。
- 每筆建議取雙方剩餘金額的最小值，直到全部結清。
- 不宣稱此演算法保證全域最少交易筆數。
- 建議只作即時計算，不直接入帳。
- UI 說明這是群組淨額結算，可能付給原本未直接替自己代墊的成員。
- 群組合計與建議應來自同一份一致資料快照。

八、還款管理

欄位：
- 付款成員、收款成員、金額、還款日期、備註。
- 登記者、建立時間、作廢時間與作廢者。

規則：
- 雙方必須是同群組的不同成員。
- 金額必須大於 0，採與支出一致的上限及精度。
- Member 可登記自己為付款方或收款方的還款。
- Owner 可代為登記任意兩位成員的還款。
- UI 明確標示「人工登記」，不表示銀行已完成付款或對方已確認。
- 不做雙方確認流程。
- 允許部分還款。
- 允許超額還款，但前端必須明確警告並要求使用者確認，因為可能形成反向欠款。
- 提供從結算建議預填還款表單的按鈕，送出前可確認金額。
- 還款不直接編輯，錯誤時先作廢再重新登記。
- 登記者或 Owner 可以作廢。
- 作廢保留歷史，重複作廢不得重複影響餘額。
- 支出與還款新增操作使用 ClientRequestId 做冪等控制。
- 同一使用者、群組、操作類型的重複 request id 不可重複入帳；相同 key 不同 payload 回 409。
- 不以金額或日期判定重複，因為真實交易可能相同。

十二、測試與驗收

使用 xUnit 或適合目前 .NET 的測試工具。
前端採相容的單元測試工具；E2E 可使用 Playwright。

核心單元測試：
- 整除與無法整除的平均分攤。
- 100 元三人分攤。
- 0.01 元三人分攤。
- 自訂分攤總額不符、負數、重複成員。
- 付款人未參與分攤。
- 金額上限與溢位。
- 多筆支出、部分還款、超額還款、作廢還款。
- 修改或刪除已有還款的支出。
- 所有成員餘額總和永遠為 0。
- 結算建議套用後全部餘額為 0。
- 演算法輸出順序穩定。

SQL Server 整合測試：
- 使用獨立測試資料庫，禁止對非測試資料庫清理或重建。
- Migration 可在空資料庫執行。
- 唯一約束、FK、交易回滾、樂觀鎖定。
- 跨群組讀寫遭拒。
- 非 Owner 無法管理邀請或移除成員。
- 無法修改他人建立的支出。
- 有歷史帳務關聯的成員無法移除。
- 並行接受邀請只產生一筆成員資料。
- 重複送出支出／還款不會重複入帳。
- 成員移除與帳務新增的競態條件。
- 缺少或錯誤 CSRF token 的寫入遭拒。
- 正式環境不能啟用測試身份。

至少完成一條完整 E2E：
- 使用測試環境專用登入方式建立 A、B、C。
- A 建立群組，B、C 透過邀請加入。
- A 代墊 900 元，三人平均分攤。
- B 代墊 300 元，只有 B、C 分攤。
- 驗證 A 應收 600、B 應付 150、C 應付 450。
- 記錄 B 付給 A 150、C 付給 A 450。
- 驗證三人餘額均為 0。
- 驗證群組消費總額仍為 1,200。
- 作廢 B 的還款，驗證 A 應收 150、B 應付 150、C 為 0。

Google 真實登入另外提供人工驗收清單。
不可把測試登入的成功當成 Google OAuth 已驗證。
